## 引言：为什么需要“订阅”这层设计？

在早期 Shadowsocks 时代，每搭建一台海外服务器，用户就必须手动在客户端输入一次 IP 地址、端口号、加密方式和密码。如果服务商拥有 50 个节点，用户就要手动填写 50 遍；一旦某台服务器遭遇 IP 封锁更换了地址，所有用户又得重新手动修改一遍，维护成本极高。

**“订阅系统 (Subscription System)”的诞生彻底改变了这一局面**。它让繁琐的节点管理变成了全自动化的云端动态拉取。

```mermaid
graph TD
    subgraph 云端服务商体系
        Admin[机场运维管理后台] -->|动态调整/增减维护| NodePool[实时节点数据库 (50+ 节点)]
        NodePool --> API[订阅生成接口 / API Server]
    end
    
    API -->|下发加密专属 URL (含 Token)| SubURL[你的专属订阅链接]
    
    subgraph 本地用户终端
        SubURL -->|导入并定期更新| Client[Clash / 小火箭 / v2rayN 客户端]
        Client -->|自动解析出| ParsedNodes[本地活动节点清单 (免手动配置)]
    end
```

## 一、订阅链接、服务器节点与客户端的三维关系

要彻底理解出海网络的运行，可以用一个生动的现实生活比喻：

| 角色 | 现实比喻 | 对应网络角色 | 核心职责 |
| :--- | :--- | :--- | :--- |
| **服务器节点** | 各地实体餐馆 (香港店、日本店) | 境外真实 VPS 服务器 | 负责接收并代发你的上网流量 |
| **订阅链接** | 动态订餐 App 网址 (含你的会员卡号) | 专属 HTTPS API 接口 | 告诉客户端当前有哪些餐馆营业、密码是什么 |
| **代理客户端** | 送餐骑手 / 手机操作系统 | Clash / Shadowrocket 软件 | 负责根据菜单将你的请求精准送达指定节点 |

## 二、订阅链接内部长什么样？（解密 URL 结构）

一条典型的机场订阅链接通常具有如下结构：

```text
https://sub.airportdomain.com/api/v1/client/subscribe?token=a8f93e2b1c7d4e5f&flag=clash
└─────────────────┬────────────────┘ └────────┬────────┘ └──────────┬──────────┘ └─────┬────┘
           订阅分发服务器域名             API 路径        专属鉴权 Token       格式标识
```

1. **域名与 API 路径**：机场专门用于下发配置的轻量级分发服务器。
2. **专属鉴权 Token**：代表你个人身份的一串随机密钥。服务器通过识别该 Token 确认你的套餐是否有效、剩余多少流量。
3. **格式标识 (Flag)**：告诉服务器应该返回 Clash 适用的 YAML 格式、还是小火箭适用的 Base64 格式。

## 三、为什么必须定期「更新订阅」？

服务商为了保证晚高峰的稳定性和抵御网络波动，通常会进行以下日常运维动作：
- 淘汰延迟升高的旧服务器，上线全新的千兆专线；
- 临时维护发生光缆故障的特定节点；
- 优化分流规则库（如加入新增的 AI 域名）。

如果你几个月从不更新订阅，本地客户端中保存的旧节点信息就会陆续失效超时。因此，建议在客户端设置中开启 **「打开应用时自动更新」** 或 **「每 24 小时后台静默更新」**。
